# 한국 주식 분석 앱의 데이터 수집 저장 결합 판정 설계

이 설계는 한국투자증권 Open API로 KRX·NXT를 함께 보는 개인용 Mac 로컬 서버의 데이터 흐름이다. 시장별 시간과 목표 가격은 [KRX·NXT 통합 설계](MARKETS.md)에, 데이터별 원본·읽기·복구 계약은 [데이터 저장·사용 계약](DATA_CONTRACTS.md)에, 한투 채널·API 대응은 [KIS 연동 명세](KIS_INTEGRATION.md)에 정의한다. 모의주문 dev와 실전주문 prd의 분리는 [dev·prd 거래 환경](ENVIRONMENTS.md)에, 안드로이드 읽기 경로는 [원격 모니터링](MOBILE_MONITORING.md)에 정의한다. 매매 임계값과 사건 신호의 유효기간은 데이터를 모아 검증한 뒤 설정한다.

## 1. 데이터 출처와 도착 주기

| 입력 | 제공처와 인터페이스 | 수집 주기 | 실제로 받는 것 |
| --- | --- | --- | --- |
| 시세 | 한국투자증권 웹소켓의 KRX 체결 `H0STCNT0`, NXT 체결 `H0NXCNT0` 또는 검증된 통합 체결 `H0UNCNT0`; 시장별 호가 | 거래 가능한 장 단계에서 연결 유지 | 종목코드, 시장, 장 단계, 체결 시각·가격·수량, 매수·매도 호가 등 |
| 일반 뉴스 | 네이버 뉴스 검색 REST `GET /v1/search/news.json?query=...&sort=date` | 관심 종목별 1분 | 제목, 요약, 원문 URL, 제공 시각 |
| 기업 공시 | OpenDART 공시검색 REST `GET /api/list.json` | 장 전·후 및 장중 15분 | DART 회사 고유번호, 종목코드, 접수번호, 보고서명, 접수일자 |
| 계좌 상태 | 한투 잔고·주문 조회 REST | 앱 시작, 주문 상태 변경, 정기 재확인 | 보유 수량, 사용 가능 현금, 미체결 주문 |

한투 연결 코드는 `KisMarketData`, `KisBarRecovery`, `KisAccount` 어댑터 뒤에 둔다. 체결 필드는 `MKSC_SHRN_ISCD`, `STCK_CNTG_HOUR`, `STCK_PRPR`, `CNTG_VOL`, `BSOP_DATE` 등이다. 입력마다 시장과 장 단계를 붙인다. 당일·과거 분봉 REST 조회는 앱 재시작이나 웹소켓 누락 구간 복구에 사용한다. 시장 코드는 `J`(KRX), `NX`(NXT), `UN`(통합)이다.

관심 종목의 내부 키는 6자리 `stock_code`다. OpenDART의 `corpCode.xml` 파일에서 `stock_code ↔ corp_code ↔ 정식 회사명`을 받아 저장한다. 뉴스 검색에는 정식 회사명과 확인된 별칭을 쓰고, 회사명이 같은 일반 단어로 쓰인 기사 등은 종목 관련성 판정 후 연결한다.

네이버 검색 API는 기사 전문이 아니라 제목·요약·링크를 돌려준다. 첫 버전의 Jev 입력은 이 필드로 제한한다. 공시는 목록 제목만으로 중요한 내용을 알기 어려울 때, 해당 `rcept_no`의 OpenDART 원문 파일을 추가로 받아 필요한 부분을 추출한다.

## 2. 처리 순서

### 시세

1. 웹소켓 메시지에서 종목코드, 거래 시장, 장 단계, 거래일, 체결 시각, 가격, 수량을 읽고 입력 오류와 중복을 거른다.
2. 종목·시장·장 단계별로 같은 1분 구간의 체결을 묶어 시가·고가·저가·종가·거래량을 만든다. 통합 체결을 입력으로 선택한 경우 이를 별도 통합 봉으로 만들고 개별 체결을 중복 합산하지 않는다. 최근 호가는 시장별 매수·매도 1호가로 보관한다.
3. 완성된 1분 봉은 메모리의 최신 봉 목록에 반영하고 당일 `bars.jsonl`에 한 줄씩 추가한다. Mac 저장 용량을 줄이기 위해 모든 원시 체결 틱을 장기간 보관하지 않는다.
4. 시장별·통합 봉으로 수익률·거래량 변화·변동성 등 지표를 계산한다. 종목별 작은 모델 상태를 한 단계 갱신하고 다음 1분·1시간 뒤·KRX 공식 종가·NXT 종료 기준 가격의 예상 수익률을 당일 `forecasts.jsonl`에 추가한다.
5. 한 시장의 웹소켓이 끊겼다면 그 시장을 `stale`로 표시한다. 재접속 후 제공 가능한 시장별 분봉으로 누락 구간을 채우고 종목별 모델 상태를 저장된 봉으로 다시 만든다. 복구 전의 통합 예측도 `stale`로 표시한다.

### 뉴스

1. 관심 종목 검색어별로 날짜순 최신 결과를 조회한다. 검색 결과의 `originallink`를 정규화한 URL을 기본 식별자로 쓰고, 같은 기사가 여러 검색어에 나타나면 하나만 저장한다.
2. 제목의 HTML 강조 태그를 제거하고 제목·요약·URL·제공 시각을 당일 `news.jsonl`에 추가한다. 기사 최초 발견 시각 `first_seen_at`은 앱 시계로 별도 기록한다.
3. 회사명 충돌이나 동명 기사를 걸러 종목 연결을 같은 항목의 `stock_codes`에 기록한다. 필요한 경우 Jev가 실제 종목 관련성과 사건 유형을 분류한다.
4. Jev 분석이 끝나면 종목별 결과와 `available_at = 분석 완료 시각`을 당일 `signals.jsonl`에 추가한다. 새 결과가 생겼을 때만 해당 종목을 다시 판정한다.

### 공시

1. 관심 회사의 `corp_code`로 오늘과 누락 가능 구간의 목록을 조회한다. `last_reprt_at=N`으로 정정보고서를 포함하고, `rcept_no`를 기본 키로 사용한다.
2. 새 목록 항목을 당일 `filings.jsonl`에 추가한다. 필요할 때만 `document.xml` 원문을 요청해 `originals/dart/{rcept_no}.zip`으로 보관하고 핵심 문단을 추출한다. 정정공시는 새 접수번호로 저장하면서 이전 건과 연결한다.
3. 목록 제목과 추출한 본문으로 Jev가 사건 유형, 해당 종목 관련성, 불확실성을 분류한다. 분석 결과의 `available_at`을 기록하고 종목을 다시 판정한다.

수집과 Jev 요청은 비동기 작업이다. Jev 요청이 늦거나 실패해도 시세 웹소켓과 1분 봉 계산은 계속된다. 각 항목의 처리 상태는 `new → analyzing → ready` 또는 `retry`로 남겨 재시작 후 이어서 처리한다.

### 비동기 작업과 큐

| 작업 | 입력 → 출력 | 지연·실패 처리 |
| --- | --- | --- |
| 웹소켓 수신 | 증권사 메시지 → 크기 제한이 있는 시세 큐 | 메시지 해석이나 Jev 호출을 기다리지 않음. 큐 초과·연결 끊김은 누락 구간으로 기록 |
| 봉 계산·가격 추론 | 시세 큐 → 종목별 봉·예측 → 판정 요청 | 종목별 시각 순서 유지. 모델 계산이 이벤트 루프를 오래 점유하면 별도 실행 작업으로 이동 |
| 뉴스·공시 수집 | 각 API → 신규 항목 파일 → 텍스트 분석 큐 | 조회 주기는 독립 실행. 일시 실패 시 겹치는 기간을 재조회 |
| Jev 사건 분석 | 텍스트 분석 큐 → 종목별 사건 신호 | 동시 요청 수·대기열 크기·시간 제한 설정. 실패 항목만 재시도 |
| 매매 판단 | 새 봉 또는 사건 신호 → 최신 snapshot → 필요할 때 Jev 후보 요청 | 같은 종목의 잦은 요청은 최신 상태로 합침. 오래된 응답은 확정하지 않음 |
| 파일 기록·DB 인덱스 | 확정된 사건·판정 → 환경별 JSONL → 환경별 DynamoDB | 파일 기록을 먼저 완료. DB 중단 시 누락 인덱스를 나중에 재생 |
| 모바일 모니터링 게시 | 확정된 최신 상태·주요 이벤트 → 환경별 monitor outbox → AWS 모니터링 테이블 | AWS 장애 시 재시도하고 화면에 게시 지연 표시. 시세·판정·주문은 게시 완료를 기다리지 않음 |

시세 큐가 가득 차면 체결 메시지를 조용히 버리고 정상 봉으로 취급하지 않는다. 해당 종목에 `gap` 표시를 하고 신규 매매 후보를 보류한 뒤 분봉 REST로 빠진 구간을 보정한다. 보정된 봉을 시간순으로 다시 적용해 모델 상태를 복원한다. 뉴스·공시 분석 큐가 가득 차면 수집한 원본을 파일에 남기고 Jev 분석을 뒤로 미룬다. 이때 사건 신호의 `available_at`은 실제 분석 완료 시각이다.

판정용 Jev 요청에는 봉·예측·신호·계좌의 버전 ID를 함께 붙인다. 응답 시 버전이 달라졌으면 결과를 `superseded`로 기록하고, 최신 snapshot이 여전히 후보 조건을 만족할 때만 다시 요청한다. 큐 길이, 미분석 항목 수, 가장 오래된 항목의 대기 시간, 누락 봉 수, Jev 응답 시간을 화면에서 관찰한다.

## 3. 로컬 파일과 DynamoDB 저장 구조

장중의 최신 상태는 환경별 메모리에 둔다. Mac의 환경별 날짜별 JSONL 파일을 원본 기록으로 삼고, 장 마감 후 시계열을 Parquet로 정리해 학습·검증에 사용한다. dev DynamoDB Local과 prd 관리형 DynamoDB에는 각각의 작은 뉴스·공시 신호와 판정 메타데이터를 비동기로 인덱싱한다. 매분 판정할 때 DB를 조회하지 않는다.

dev는 AWS의 **DynamoDB Local**을 전용 서비스와 볼륨에서 실행한다. Docker 이미지 또는 Java 실행 파일로 구동하고, `-sharedDb -dbPath`로 데이터 파일을 영구 보관한다. dev의 로컬 인덱스 자체에는 AWS 사용료가 들지 않지만 안드로이드 모니터링을 위한 AWS dev 테이블·API에는 사용량 비용이 든다. prd는 별도 관리형 DynamoDB 테이블·접근 권한을 사용한다. DynamoDB Local은 AWS가 개발·시험용으로 제공하므로 실전 주문을 수행하는 prd의 DB로 사용하지 않는다. 원본 JSONL·Parquet와 DB 데이터는 환경별로 백업한다. [AWS 설치 안내](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html), [로컬 사용 시 차이](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.UsageNotes.html).

```text
data/<environment>/                   dev 또는 prd의 전용 볼륨
  config/watchlist.json                 관심 종목, 회사 코드, 검색 별칭
  state/collectors.json                마지막 성공 조회 시각과 재시도 상태
  hot/2026-10-25/bars.jsonl            완성된 1분 봉
  hot/2026-10-25/forecasts.jsonl       가격 모델 예측값
  hot/2026-10-25/news.jsonl            새 기사 제목·요약·원문 URL
  hot/2026-10-25/filings.jsonl         새 공시 메타데이터
  hot/2026-10-25/signals.jsonl         Jev 사건 분류 결과
  hot/2026-10-25/accounts.jsonl        계좌 상태 조회 기록
  hot/2026-10-25/decisions.jsonl       사용 데이터 ID·핵심 값·판정 결과
  hot/2026-10-25/orders.jsonl          주문 의도·접수·거부·체결·취소·대조 결과
  hot/2026-10-25/sync_outbox.jsonl     로컬·클라우드 인덱스 대상 항목의 식별자
  hot/2026-10-25/monitor_outbox.jsonl  AWS 모바일 모니터링 게시 대상과 버전
  state/sync_checkpoint.json          인덱스 동기화가 끝난 항목의 위치
  state/monitor_checkpoint.json       모니터링 게시 완료 위치
  state/monitor_versions.json         항목별 단조 증가 스냅샷 버전
  dynamodb/                           dev 전용 DynamoDB Local 데이터 파일과 백업
  originals/dart/{rcept_no}.zip        필요할 때 받은 공시 원본
  parquet/bars/year=2026/month=10/*.parquet
  parquet/forecasts/year=2026/month=10/*.parquet
  parquet/decisions/year=2026/month=10/*.parquet
  reports/                             학습 특징·백테스트 결과 파일
  models/{version}/                    모델 가중치, 정규화 값, 특징 정의
```

JSONL 한 줄에는 환경(`dev` 또는 `prd`), 식별자, 종목코드, 제공처 시각, 앱 수신 시각, 형식 버전을 명시한다. `bars.jsonl`의 논리 키는 `(stock_code, venue, market_phase, minute_at)`이며 통합 봉에는 `venue=COMBINED`를 쓴다. `news.jsonl`은 정규화한 원문 URL의 해시, `filings.jsonl`은 `rcept_no`다. 재접속 복구로 봉을 정정할 때는 원래 줄을 덮어쓰지 않고 같은 키의 새 버전을 추가한다. 조회와 Parquet 정리 시 키별 최신 버전 하나만 선택한다.

파일 쓰기는 서버의 한 작업 큐가 처리한다. `collectors.json`은 임시 파일을 쓴 뒤 이름을 바꿔 갱신한다. 앱 재시작 시 최근 JSONL과 이전 Parquet를 읽어 종목별 최신 봉·신호·중복 식별자를 메모리에 복원한다. 모델의 LSTM 내부 상태는 최근 봉을 순서대로 재생해 복원한다. 외부 API 키는 별도 보안 저장소에 둔다. DynamoDB Local용 SDK에는 형식상 리전과 자격 증명이 필요하지만 실제 AWS 키는 사용하지 않는다.

`sync_outbox.jsonl`은 로컬 원본 기록이 성공한 뒤 만들고, 별도 작업이 해당 환경의 DynamoDB에 쓴다. DB 서비스가 멈춰도 수집·추론·판정은 계속한다. 복구 후 미처리 항목을 재시도한다. 로컬 파일과 DB 사이에는 단일 트랜잭션이 없으므로 같은 항목을 다시 써도 결과가 같도록 고정된 식별자와 조건부 쓰기를 사용한다. 처리 완료 위치는 별도 체크포인트에 원자적으로 기록한다. 재시작할 때 로컬 원본과 outbox를 대조해 누락된 항목을 만들고 미처리 항목을 다시 쓴다. 같은 날짜의 JSONL과 파생 Parquet를 분석할 때는 한쪽만 선택해 이중 집계하지 않는다.

환경별 DynamoDB의 `app_events` 테이블은 `PK = SYM#<stock_code>`, `SK = <kind>#<UTC시각>#<고정ID>`로 둔다. `kind`는 `NEWS`, `DART`, `SIGNAL`, `DECISION` 등이다. 각 항목에 원본 ID와 거래일, `available_at`, 분류, 모델·규칙 버전을 저장한다. 원본은 ID와 거래일로 로컬 파일에서 찾으므로 파일 절대 경로나 줄 번호를 인덱스에 저장하지 않는다. 같은 뉴스가 여러 종목에 연결되면 종목별 작은 항목을 하나씩 기록한다. `PutItem`의 조건부 쓰기로 재처리 중 중복 생성을 막는다. 종목과 종류·시간 범위로 `Query`할 수 있지만, 장중 판정에 필요한 신호는 이미 메모리에 있다. `STATE#LATEST` 같은 별도 정렬 키에는 화면에 필요한 최신 상태만 덮어쓸 수 있다. 계좌 원장과 전체 시세 틱, 기사 전문, 공시 원본은 로컬 파일에 보관한다. DynamoDB 항목은 최대 400KB이므로 긴 본문을 한 항목에 넣지 않는다.

| 데이터 | 원본 기록 | 환경별 DynamoDB의 역할 | 장중 읽기 |
| --- | --- | --- | --- |
| 완성된 1분 봉·모델 예측 | 당일 JSONL, 마감 후 Parquet | 기본 설계에서는 저장하지 않음 | 종목별 메모리 상태 |
| 뉴스·공시 메타데이터와 원문 | JSONL, 필요한 원문은 별도 파일 | 종목·시각별 작은 사건 인덱스 | 관련 신호만 메모리 |
| Jev 사건 신호·매매 판정 | JSONL | 이력 검색용 인덱스와 최신 화면 상태 | 최신 신호·판정은 메모리 |
| 계좌·주문 상태 | 로컬 JSONL | 기본 설계에서는 저장하지 않음 | 최신 확인값을 메모리 |

판정 인덱스의 작은 속성에는 사용한 시장·장 단계, 주문 가능 시장, 선택한 한투 주문 경로(`KRX`, `NXT`, `SOR`)와 그때의 호가 시각도 넣는다. NXT 대상 종목 목록과 시장별 휴장·중단 상태는 날짜별 원본 파일로 기록하고 장중 메모리에 반영한다.

파일의 각 기록에는 `event_id`, `schema_version`, `source_at`, `received_at`을 넣는다. Jev 결과에는 `available_at`, `model_version`, 원본 `event_id`를 추가한다. 같은 작업의 재시도는 같은 ID를 사용한다. 사건을 새로운 모델 버전으로 재분석한 경우에는 새 분석 ID와 `available_at`을 부여해 이전 판단을 바꾸지 않는다. 판정 기록에는 `decision_id`, 발생 원인(`bar` 또는 `signal`), 사용한 봉·예측·신호·계좌 버전 ID, 후보와 최종 결과를 넣는다. 이 ID들이 있어야 나중에 당시 입력을 정확히 재구성할 수 있다.

로컬 JSONL 추가가 성공해야 메모리에 새 신호·판정을 확정한다. 그 뒤 인덱스 작업을 생성한다. DB 인덱싱이 늦어져도 판정에는 영향을 주지 않는다. JSONL 추가 자체가 실패하면 해당 입력은 미확정으로 표시하고 매매 후보를 내지 않는다. 화면의 실시간 상태는 메모리에서 제공하고, 과거 사건·판정 검색은 해당 환경의 DynamoDB를 사용한다.

`signals.jsonl`의 `available_at`은 **Jev 분석 결과를 실제로 사용할 수 있게 된 시각**이다. 뉴스 `pub_at`이나 공시 `rcept_dt`만으로 과거 장중 시각의 사용 가능 여부를 결정하지 않는다. 특히 공시 목록의 `rcept_dt`는 날짜 단위다. 앱이 꺼져 있던 동안 나온 기사를 나중에 가져왔다면, 그 기사를 앱이 과거에 이미 알고 있었던 것으로 처리하지 않는다.

관련 AWS 문서: [DynamoDB 정렬 키](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-sort-keys.html), [조건부 쓰기](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [항목 크기 제한](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html).

모바일에 필요한 종목·계좌·상태 스냅샷과 주요 사건·주문 이벤트는 별도의 `monitor_outbox.jsonl`을 거쳐 AWS dev/prd 모니터링 테이블에 게시한다. 이 큐는 로컬 검색 인덱스용 `sync_outbox.jsonl`과 체크포인트를 공유하지 않는다. 게시가 늦거나 실패해도 장중 매매 판단과 한투 주문은 로컬 원본·계좌 상태를 사용한다. 안드로이드에서의 조회 형식과 최신성 표시는 [원격 모니터링](MOBILE_MONITORING.md)을 따른다.

## 4. 세 흐름을 한 종목에 모으는 방법

### 매분 계산하는 가격 목표

방금 완성된 통합 1분 봉의 기준 가격을 `C_t`라고 한다. “다음 가격”은 다음 체결 틱이 아니라 **1분 뒤의 유효한 가격**으로 정의한다. 예측 모델의 출력은 가격 자체보다 수익률 `r_1m`, `r_60m`, `r_krx_close`, `r_nxt_end`로 학습하고, 화면에는 `C_t × (1 + r)`로 환산한 가격을 표시한다. 종료 목표를 두 개로 나눈 이유는 KRX 공식 종가와 NXT 애프터마켓 종료 기준 가격이 다른 시각·다른 값이기 때문이다. 네 출력을 공유 상태를 가진 작은 모델의 별도 헤드로 만들 수 있으며, 먼저 각 목표의 단순 기준선과 비교한다.

| 출력 | 목표 가격 | 예측 당시 사용 조건 | 매매 판단에서의 역할 |
| --- | --- | --- | --- |
| `p_1m` | 1분 뒤 통합 기준 가격 | 현재 시세가 신선하고 목표 시각이 계획상 연속매매 구간 | 진입 시점과 단기 급변 위험 확인 |
| `p_60m` | 60분 뒤 통합 기준 가격 | 현재 시세가 신선하고 목표 시각이 계획상 연속매매 구간 | 단기 보유의 주된 방향 판단 |
| `p_krx_close` | 당일 KRX 공식 종가 | 15:30 종가 확정 전 | KRX 정규장 종료 방향 판단 |
| `p_nxt_end` | 당일 NXT 애프터마켓 종료 전 마지막 유효 체결가 | NXT 거래 대상이고 현재 거래 상태가 정상이며 종료 전 | NXT 애프터마켓 종료 방향 판단 |

NXT는 프리·메인·애프터마켓으로 나뉘고 KRX는 시가·종가 동시호가 구간이 있다. 1분·60분 목표가 계획된 휴장 또는 동시호가 구간에 걸리면 예측 당시 `usable=false`로 기록한다. 실제 미래 목표 시각에 체결이 없었는지는 나중에 확인해 학습용 `label_valid`에만 반영한다. 60분 뒤 다른 연속매매 장 단계에서 거래가 재개된다면 그 단계의 가격을 정답으로 사용할 수 있지만, 현재와 목표의 장 단계를 입력·평가에서 구분한다. 15:30 이후 KRX 종가는 이미 알려진 관측값이므로 `p_krx_close`를 새 예측으로 취급하지 않는다. NXT의 종료 기준 가격은 KRX 공식 종가가 아니다. 마감 동시호가 구간의 매매는 별도 규칙이 검증되기 전까지 보류한다. 자세한 시각과 목표 정의는 [KRX·NXT 통합 설계](MARKETS.md)에 둔다.

`forecasts.jsonl`에는 `stock_code`, 기준 봉 ID·시각·가격, 현재 시장·장 단계, 네 목표의 예상 수익률·환산 가격·목표 시각·예측 당시의 `usable`, 모델 버전, 생성 시각을 한 기록으로 남긴다. 종료 예측에는 남은 장 시간과 현재 장 단계를 특징으로 넣는다. 학습·평가에서는 날짜 순서로 분리하고, 목표 시점이 없는 출력은 사후 `label_valid=false`로 표시해 손실 계산에서 제외한다. 검증 구간의 목표별·장 단계별 예측 오차로 불확실성 범위를 추정해 예상 순수익과 함께 저장한다. 매매 평가는 예측 기준 봉의 종가에 즉시 체결된 것으로 가정하지 않고, 추론과 판정이 끝난 뒤 실제 이용 가능한 시장별 매수·매도 호가를 사용한다.

판정 시각 `T`, 종목 `S`가 정해지면 다음 순서로 **그 시각에 이용 가능했던 최신 데이터**를 고른다.

1. 메모리의 `bars_1m`에서 `S`의 가장 최근 완성된 시장별·통합 봉과 시장별 호가를 읽는다.
2. 메모리의 `forecasts`에서 그 봉으로 계산한 최신 예측을 읽는다. 예측 시각과 버전이 맞지 않으면 판정을 보류한다.
3. 메모리의 `event_signals`에서 `stock_code=S`, `available_at ≤ T`, 아직 유효한 새 뉴스·공시 신호를 읽는다. 이미 반영한 동일 이벤트는 중복 반영하지 않는다.
4. 가장 최근 계좌 스냅샷에서 보유량·현금·미체결 주문을 읽는다. 계좌 정보가 오래됐으면 주문 후보는 보류한다.
5. 코드에서 현재 거래 가능한 시장의 매수·매도 호가와 `p_60m`·현재 장 단계의 종료 목표를 비교해 수수료·세금·스프레드·예상 미끄러짐을 반영한 기간별 예상 순수익과 최대 주문 가능 수량을 계산한다. `p_1m`은 급한 진입·청산의 위험 신호로 사용한다.

이렇게 만든 하나의 `decision_snapshot`에는 **종목, T, 거래 가능한 시장과 장 단계, 시장별 가격·호가, 네 예측값과 유효 여부, 관련 이벤트 ID 및 사건 분류, 포지션, 비용, 각 데이터의 마지막 갱신 시각**이 들어간다. 이 객체는 먼저 메모리에서 조립한다. 예를 들어 10:15 판정에는 10:15까지 완성된 가격 정보와 10:15 이전에 분석이 끝난 기사·공시만 넣는다. 이후 들어온 공시를 10:15 판정에 소급하지 않는다.

판정이 끝나면 로컬 `decisions.jsonl`에 그때 사용한 봉·예측·이벤트의 ID, 핵심 숫자, 판정 후보와 최종 결과를 작은 불변 스냅샷으로 추가한다. 기사 본문이나 모든 1분 봉을 복사해 넣지 않는다. 원본은 각각 로컬 시세·뉴스·공시·신호 파일에 한 번만 보관한다. 이 판정 기록의 작은 검색용 사본은 outbox를 거쳐 DynamoDB에 전송한다. 따라서 `decision_snapshot`은 **그 판단을 나중에 재현할 수 있게 하는 기록**이다.

## 5. Jev 판정과 최종 제약 검사

매수·매도의 기본 후보는 현재 장 단계에서 유효한 예측과 시장별 체결 비용을 코드에서 계산해 만든다. 새 뉴스·공시의 **사건 분류**에는 Jev를 사용한다. 가격 기준을 통과한 후보나 새 사건 신호가 있을 때에만 Jev에 정리된 snapshot을 보내 사건과 가격 판단의 충돌 여부를 분류하게 할 수 있다. Jev의 확률은 미래 수익률 확률이 아니며, 수익률·시간·주문 수량 계산은 코드에서 한다.

```text
새 1분 봉 또는 새 event_signal이 준비되면:
  snapshot = 종목 S의 시각 T 기준 최신 사용 가능 데이터 결합
  if 입력 누락 또는 시세·계좌 데이터가 오래됨: HOLD(사유 코드)
  else:
      net_60m, net_session_end = 시장별 매수·매도 호가와 거래비용 기준 예상 순수익 계산
      if p_60m 또는 현재 장 단계의 종료 목표가 무효: 신규 진입은 HOLD(목표 시각 없음)
      elif 두 기간의 순수익이 각각 매수 기준을 넘고 p_1m 급락 위험이 낮음:
          code_candidate = BUY
      elif 보유 중이고 두 기간의 순수익이 각각 매도 기준 아래임:
          code_candidate = SELL
      else: code_candidate = HOLD
      if 위험 한도 초과 또는 손절 등 별도 청산 조건: code_candidate = SELL 또는 HOLD
      if code_candidate가 HOLD이고 새 사건 신호도 없음: 최종 HOLD
      elif 동일한 입력 ID 조합을 이미 판정했거나 종목별 Jev 호출 간격 이내:
          기록된 사건 판단과 코드 제약으로 확정 또는 HOLD
      else:
          event_review = Jev(snapshot의 요약과 후보의 근거·충돌 여부)
          if Jev 실패/시간 초과: 신규 진입은 HOLD(미확정)
          else: 사건 충돌을 반영하고 코드로 잔고·보유량·한도·중복 주문 재검사
  결정과 snapshot의 ID·버전을 decisions에 저장하고 화면에 표시
```

이 표의 매수·매도 기준은 초기 정책 예시이며, 각 임계값과 `p_1m` 위험 기준은 시간순 검증으로 정한다. 매수 후보는 예상 순수익이 거래비용뿐 아니라 검증에서 관측한 예측 오차 여유까지 넘을 때 만든다. 두 기간 예측이 충돌하면 기본값은 `HOLD`다. 1분 예측만으로 매수·매도를 반복하지 않는다. Jev 응답을 기다리는 사이 새 1분 봉이나 주문 상태가 바뀌면 낡은 snapshot으로 매매 결정을 확정하지 않고 최신 데이터로 다시 판정한다. 새 뉴스·공시의 사건 분류 호출은 각 원본과 분석 모델 버전당 한 번으로 제한한다. 화면의 판단 이유는 사건 분류와 로컬 제약 검사 결과를 사람이 읽을 수 있게 조합한다. 실제 주문 연결 시에는 이 판정 이후 별도 주문 실행기에서 재확인한다.

## 6. 최초 실행과 검증

앱 시작 시 관심 종목·회사 코드 매핑을 읽고, 최근 봉으로 모델 상태를 복원한다. 뉴스와 공시는 마지막 성공 조회 시각부터 겹치게 다시 조회하고 키로 중복 제거한다. 실패한 수집·분석 작업은 제한적으로 재시도한다.

과거 1분 봉으로 가격 모델을 학습할 때는 시간순 학습·검증·평가 기간을 분리한다. 뉴스·공시까지 포함한 매매 판단 성능은 각 항목의 실제 `available_at` 기록이 쌓인 기간에서 검증한다. 과거 기사 게시 시각만으로 당시 앱의 분석 완료 시각을 만들어내지 않는다. 거래비용과 실제 가능한 호가를 반영한 모의 매매 결과로 코드 판단기와 Jev 판단기를 비교한다.

## 7. 구현 순서와 운영 경계

1. 파일 기록기, 종목별 메모리 상태, 웹소켓 재연결·분봉 복구를 만든다. 재시작 후 오늘의 완성 봉과 중복 ID가 복원되는지 확인한다.
2. DynamoDB Local의 `app_events` 테이블과 비동기 인덱스 작업을 붙인다. DB를 중지한 상태에서도 파일 기록과 판정이 지속되는지, 재가동 후 동일 ID가 중복 없이 인덱싱되는지 확인한다.
3. 뉴스 1분 조회, 공시 장중 15분 조회, 새 항목 식별, Jev 사건 분류를 붙인다. 검색 범위는 마지막 성공 시각보다 겹치게 다시 가져오고 원본 ID로 중복을 제거한다.
4. 먼저 단순 가격 기준선과 코드 기반 판정기를 구현해 기록한다. 그다음 작은 상태 유지형 모델과 Jev 매매 후보 분류를 같은 장중 입력으로 비교한다. 최종 자금·한도·중복 주문 검사는 코드에서 수행한다.
5. 초기 구현은 주문 없이 판정의 지연, 데이터 누락률, 비용 반영 성과를 확인한다. 이후 dev의 한투 모의투자 주문·체결·취소·복구를 연결하고, [승격 조건](ENVIRONMENTS.md)을 충족한 릴리스만 prd 실전 주문에 사용한다.

앱 프로세스 재시작 시 해당 환경의 JSONL·Parquet에서 메모리 상태를 복원하고, DB 인덱스 누락분을 재생한다. dev DynamoDB Local의 데이터 파일이 손상되면 dev 원본 파일에서 테이블을 새로 만든다. prd 인덱스도 prd 원본으로 복구한다. JSONL·Parquet와 모델 파일의 환경별 백업이 우선이며 DB 인덱스는 복구 가능한 사본으로 취급한다. 주문 기능이 켜진 환경은 재시작 시 한투 주문·체결·잔고를 조회해 로컬 기록과 대조한 뒤 신규 주문을 재개한다. 장 마감 Parquet 변환은 임시 파일을 완성한 뒤 교체하고, 변환이 끝난 날짜의 JSONL은 백업·검증 전까지 삭제하지 않는다.
