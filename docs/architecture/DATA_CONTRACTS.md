# 데이터 저장·사용 계약

이 문서는 [전체 구조](ARCHITECTURE.md), [수집·판정 흐름](DATA_PIPELINE.md), [KRX·NXT 시장 경계](MARKETS.md)를 구현할 때 데이터가 어디서 생성되고 어디에 남으며 누가 읽는지 정의한다. 초기 단계는 판단·시뮬레이션을 기록하고, 이후 [환경별 주문 계약](ENVIRONMENTS.md)에 따라 dev 모의계좌와 prd 실전계좌의 거래를 기록한다. 안드로이드용 사본과 조회 API는 [원격 모니터링](MOBILE_MONITORING.md)에 정의한다.

## 저장소의 책임

| 위치 | 책임 | 장중 판정에서의 사용 |
| --- | --- | --- |
| 메모리 | 종목·시장별 최신 봉과 호가, 모델 상태, 예측, 사건 신호, 계좌 상태 | 읽기와 결합의 기본 경로 |
| 날짜별 JSONL | 완성 봉, 예측, 뉴스·공시, 분석 신호, 계좌 조회, 판단의 변경 불가 원본 기록 | 기록 완료 뒤 메모리에 공개; 재시작 때 재생 |
| Parquet | 검증된 날짜의 봉·예측·판단을 학습·백테스트용으로 정리 | 장중 판정에는 사용하지 않음 |
| 원문 파일 | 필요 시 내려받은 공시 원본 등 큰 자료 | Jev 입력 추출·감사 때 사용 |
| 환경별 DynamoDB | dev는 Local, prd는 관리형 서비스로 종목별 사건·신호·판단 이력 검색과 화면용 최신 상태 제공 | 장중 판단의 필수 입력으로 사용하지 않음 |
| AWS 모니터링 테이블 | dev·prd별 작은 최신 스냅샷과 주요 이벤트 사본 | 안드로이드 조회 전용; 매매 판단·주문에는 사용하지 않음 |

시세 체결 메시지는 수신 직후 봉 생성에 사용하지만, 첫 버전은 모든 원시 틱을 장기 보관하지 않는다. 완성된 시장별·통합 1분 봉을 원본 시계열로 보관한다. 통합 체결 채널을 기준 입력으로 선택하면 개별 시장 체결을 다시 합산하지 않는다. 체결의 고유 순번이 제공되지 않는 경우 동일 시각·가격·수량만으로 중복이라고 판정하지 않는다.

## 데이터별 쓰기·읽기

| 데이터 | 생성 시점과 최소 필드 | 영구 저장 | 소비자 |
| --- | --- | --- | --- |
| `bar_1m` | 봉 완성 시: `bar_id`, 종목, `venue`, `market_phase`, 시작·종료 시각, OHLCV, 완전성, 수정 버전 | `bars.jsonl` → Parquet | 가격 모델, 복구, 학습 |
| `quote_latest` | 호가 수신 시: 종목, 시장, 최우선 매수·매도 가격/수량, 제공 시각, 수신 시각 | 판정에 쓰인 값은 `decision`에 복사; 전체 호가 스트림은 장기 보관하지 않음 | 비용·주문 경로 검사 |
| `forecast` | 봉 처리 완료 시: `forecast_id`, 기준 `bar_id`, 모델 버전, 네 목표의 값·목표 시각·당시 `usable`·오차 범위, 생성 시각 | `forecasts.jsonl` → Parquet | 판단기, 평가 |
| `news_item` | 기사 최초 발견 시: 원문 URL 해시, 제목·요약·링크, 게시 시각, 최초 발견 시각, 관련 종목 | `news.jsonl` | Jev 사건 분석, 검색 인덱스 |
| `filing_item` | 공시 최초 발견 시: `rcept_no`, 회사·종목 코드, 보고서명, 접수일, 최초 발견 시각, 정정 관계 | `filings.jsonl`, 필요한 원문 ZIP | Jev 사건 분석, 검색 인덱스 |
| `event_signal` | Jev 완료 시: `signal_id`, 원본 ID, 종목, 사건 분류, 분석 모델 버전, `available_at`, 처리 상태 | `signals.jsonl` | 판단기, 검색 인덱스 |
| `account_snapshot` | 계좌 조회·주문 상태 변경 시: `account_version`, 현금, 보유량, 미체결 주문, 확인 시각 | `accounts.jsonl` | 주문 가능 수량·중복 검사 |
| `decision` | 판정 확정 시: `decision_id`, 사용한 봉·예측·신호·계좌 ID, 시장별 호가, 예상 순수익, 후보·최종 결과, 주문 경로·이유, 규칙 버전 | `decisions.jsonl` → Parquet | 화면, 평가, 검색 인덱스 |
| `order_intent`·`order_event` | 주문 제안 확정 및 접수·거부·부분 체결·체결·취소 시: 환경, 계좌 별칭, 결정 ID, 클라이언트 주문 ID, 브로커 주문 ID, 시장·수량·가격·상태·확인 시각 | 환경별 `orders.jsonl` | 주문 실행기, 계좌 복구, 감사 |

모든 시각은 저장 시 시간대가 분명한 ISO 8601 형식으로 기록한다. 제공처가 공시 접수 **날짜만** 주면 시간 값을 만들어 넣지 않고 날짜와 `precision=date`를 기록한다. 시장 단계 판단에는 한국 표준시와 해당 거래일 달력을 사용한다. 각 기록에는 `schema_version`, 원천 시각, 앱 수신 시각, 해당 기록이 판정에 이용 가능해진 시각을 구분한다. 특히 `event_signal.available_at`은 기사 게시나 공시 접수 시각이 아니라 Jev 분석 완료 시각이다.

`forecast.usable`은 예측 당시의 일정·현재 시세만으로 정한다. 목표 시각의 실제 체결 유무와 정답 품질은 그때가 지난 뒤 `label_valid`로 따로 기록한다. 실시간 판정은 `label_valid`를 읽지 않는다.

## 장중 읽기 순서와 쓰기 경계

1. KRX·NXT 웹소켓 수신 작업이 종목·시장 정보를 붙여 시세 큐에 넣는다. 시장별 봉 작업은 시각 순서대로 완성 봉을 만든다.
2. 완성 봉을 JSONL에 기록한 뒤 메모리의 최신 봉을 갱신한다. 가격 모델은 **종목당 1분에 한 번**, 통합 봉과 같은 시각의 시장별 특징을 한 입력으로 묶어 상태를 갱신한다. 시장별 봉마다 모델 상태를 여러 번 전진시키지 않는다. 네 목표의 `forecast`를 기록한 뒤 메모리에 공개한다.
3. 뉴스·공시 수집 작업은 원본 메타데이터를 기록하고 Jev 분석 작업을 큐에 넣는다. 분석이 끝나면 `event_signal`을 기록한 뒤 메모리에 공개한다.
4. 새 예측 또는 신호가 공개되면 판단 작업이 메모리의 최신 계좌·시장별 호가를 포함한 `decision_snapshot`을 만든다. 각 입력 ID와 호가 시각을 고정한 뒤 코드 후보와 필요한 Jev 검토를 수행한다.
5. 결과가 돌아왔을 때 입력 버전과 시장 상태를 다시 확인한다. 유효한 판단을 `decisions.jsonl`에 기록한 뒤 화면에 공개한다. 사건·판단의 작은 검색용 항목은 뒤에서 해당 환경의 DynamoDB에 쓴다.

파일 기록 실패, 필요한 시장의 시세 누락, 오래된 호가·계좌, 무효인 목표 중 하나가 발생하면 신규 진입 후보는 `HOLD`로 기록한다. 위험 청산은 별도 규칙과 실제 주문 가능 시장 상태를 확인한다. Jev 지연은 시세 수신과 가격 예측을 막지 않는다. 주문 기능이 켜진 경우 `decision` 뒤에 환경별 `order_intent`를 먼저 기록하고 KIS 주문을 보낸다. 재시작과 응답 시간 초과 시 해당 환경의 KIS 주문·체결·잔고를 대조한다.

## 검색 인덱스와 재시작

환경별 DynamoDB의 `app_events`는 `PK=SYM#<stock_code>`, `SK=<kind>#<UTC시각>#<고정ID>`로 사건·신호·판정을 찾는다. 항목에는 검색에 필요한 작은 요약과 `event_id`, 거래일, 시장·장 단계만 넣는다. 로컬 파일의 절대 경로나 줄 번호는 기록하지 않는다. 원본 조회는 `event_id`와 거래일로 파일·Parquet를 찾는 로컬 해석기가 담당한다. 파일 이동·Parquet 변환 후에도 이 참조는 유지된다.

시작할 때 마지막 완전한 JSONL 줄까지만 읽고, 같은 논리 키의 가장 높은 수정 버전을 선택한다. 보관된 Parquet와 당일 JSONL이 겹치면 동일 기록을 한 번만 재생한다. 장 단계 경계와 누락 봉을 고려해 종목당 시간순 통합 입력을 한 번씩 재생하여 모델 상태를 다시 만든다. 해당 환경의 DynamoDB가 비어 있거나 멈췄으면 파일의 사건·판정 ID로 검색 인덱스를 재구축한다. 인덱스 쓰기는 고정 ID와 조건부 쓰기를 사용해 재시도해도 중복되지 않게 한다.

## 구현 전 확인할 항목

- 한투 계좌 권한: KRX·NXT·통합 체결/호가 채널, 시장별 과거 분봉 조회 범위, `KRX`·`NXT`·`SOR` 주문 경로의 실제 사용 가능 여부.
- 통합 체결 채널의 실제 시장 식별 필드와 개별 채널과의 중복 관계.
- KRX 공식 종가, NXT 거래 대상 종목 변경, 당일 시장 상태를 가져올 제공처와 갱신 절차.
- 종목·장 단계별 예측 오차, 시세·호가·계좌 최신성 한도, Jev 호출 제한, 매매 임계값과 파일 보존 기간.
- dev·prd 각각의 체결 통지, 주문 취소·정정, 중복 방지와 장애 복구 절차. 초기 판정 단계 다음에 dev 모의투자 API 주문을 연결하고 검증 후 prd 실전 주문을 연다.
