지난 글에서는 왜 이 프로젝트를 시작했는지 이야기했다. 이번에는 사용하지 않고 있던 Mac 위에 어떤 시스템을 만들지 전체 구조를 그려보려 한다.

장중에는 가격이 계속 바뀐다. 뉴스는 기사마다 다른 시각에 나오고, 공시는 또 다른 경로로 도착한다. 이 정보가 모두 준비될 때까지 기다렸다가 한꺼번에 처리할 수는 없다. 그래서 설계의 출발점을 **서로 다른 속도로 들어오는 정보를 모아, 그 시점에 가능한 판단을 남기는 것**으로 잡았다.

아직 구현 전 설계다. 실제 연결과 모의투자 결과를 보면서 바뀔 수 있다.

## 전체 흐름부터 보기

시스템의 중심은 로컬 Mac이다. 한국투자증권에서 KRX·NXT 시세와 계좌 정보를 받고, 뉴스와 공시는 별도 경로로 가져온다. 가격 예측과 사건 분석 결과를 종목별로 모아 매매를 판단한다.

```text
한국투자증권 시세 ─→ 1분 봉 · 가격 예측 ─┐
뉴스 ────────────→ 새 기사 · AI 분석 ────┼→ 매매 판단 → 주문 실행 → 한투 계좌
공시 ────────────→ 새 공시 · AI 분석 ────┤       ↑
한국투자증권 계좌 ─→ 잔고 · 미체결 주문 ──┘       │
                                               │
                         판단과 주문을 로컬에 기록
                                   │
                      AWS에 모니터링용 상태 게시
                                   ↓
                              안드로이드 앱
```

그림에서는 한 줄로 이어져 보이지만, 실제 수집과 분석은 각각 독립적으로 움직일 계획이다. 뉴스 분석이 늦어져도 시세를 받는 작업은 계속되어야 한다. AWS 연결이 잠시 끊겨도 로컬의 판단과 주문 경로가 멈추지 않아야 한다.

## 세 가지 데이터 흐름

**시세**는 한국투자증권 웹소켓으로 받는다. KRX와 NXT는 거래 시간과 상태가 다르므로 어느 시장에서 언제 들어온 가격인지 구분한다. 체결 데이터를 1분 단위로 묶고, 완성된 봉을 가격 모델에 전달한다. 모델은 다음 1분, 1시간 뒤, KRX 종가와 NXT 거래 종료 기준 가격을 예측하는 방향으로 실험할 생각이다. 처음에는 단순한 예측 방법을 기준선으로 만들고, 작은 상태 유지형 모델이 실제로 더 나은지 비교한다.

**뉴스**는 관심 종목의 새 기사를 주기적으로 확인한다. **공시**는 OpenDART에서 새 접수 건을 확인한다. 같은 기사나 공시를 반복 분석하지 않도록 식별자를 남기고, 새 항목만 Jev에 보내 사건의 성격과 종목 관련성을 살핀다. AI가 반환한 결과는 가격 예측과는 별개의 신호로 기록한다. 기사 게시 시각과 시스템이 분석을 끝낸 시각도 구분할 예정이다. 그래야 나중에 과거 매매를 평가할 때 당시에는 아직 몰랐던 정보를 사용하지 않는다.

**계좌 상태**도 판단에 필요한 입력이다. 예측이 좋아 보여도 보유 수량, 사용 가능한 현금, 이미 넣은 주문, 현재 시장 상태를 모르고 주문할 수는 없다. 이 정보는 한국투자증권에서 조회하고, 주문 직전에 다시 확인한다.

## 판단과 주문을 나누는 이유

새 1분 봉이 완성되거나 관련 뉴스·공시의 분석이 끝나면 해당 종목을 다시 판단한다. 그때 사용할 예측, 사건 신호, 계좌 상태와 시세의 시각을 하나의 기록으로 묶는다. 데이터가 오래됐거나 필요한 값이 빠졌다면 새 매수 후보를 보류한다.

매매 판단기는 매수·매도·대기 후보와 이유를 만든다. 가격 예측과 Jev 분석은 여기에 참고 자료가 된다. 실제 주문을 보내는 일은 별도의 실행기가 맡는다. 실행기는 시장이 열려 있는지, 주문 가능한 수량과 가격인지, 기존 주문과 충돌하지 않는지 다시 확인한다. **AI의 출력이 곧바로 주문 요청이 되지 않게 하는 경계**다.

처음부터 주문을 보내지는 않는다. 우선 판단과 근거를 기록하면서 전략이 어떻게 동작하는지 확인하고, 다음 단계에서 모의투자 계좌에 연결한다.

## 데이터는 어디에 둘까

실시간 판단에 필요한 최신 값은 Mac의 메모리에서 읽는다. 판단할 때마다 원격 DB를 조회하면 네트워크 상태가 매매 경로에 영향을 주기 때문이다. 완성된 봉, 예측, 사건 신호, 판단과 주문 결과는 날짜별 로컬 파일에 순서대로 기록한다. 재시작하면 이 기록을 읽어 최근 상태를 다시 만든다.

장이 끝난 뒤에는 시계열 데이터를 학습과 검증에 적합한 Parquet 파일로 정리한다. DynamoDB는 뉴스·공시 신호와 판단 이력을 찾기 위한 인덱스로 사용한다. 개발 환경에서는 DynamoDB Local, 실전 환경에서는 AWS의 관리형 DynamoDB를 사용할 계획이다. 원본은 로컬 기록이며, 인덱스가 비어도 다시 만들 수 있도록 설계한다.

밖에서 상태를 확인할 수 있도록 최신 스냅샷과 주요 이벤트만 AWS에 따로 게시한다. 안드로이드 앱은 API Gateway와 Lambda를 거쳐 이 정보를 읽는다. 모바일 화면은 모니터링 용도로 두고, Mac의 판단이나 주문은 앱의 조회를 기다리지 않는다.

## 모의투자와 실전투자의 경계

같은 코드를 사용하더라도 모의투자 `dev`와 실전투자 `prd`는 별도로 운영한다. 계좌, 인증정보, 파일, DB, 주문 권한을 나눈다. 먼저 dev에서 주문·체결·취소와 장애 복구까지 시험하고, 검증한 코드와 모델 버전만 prd에 적용할 생각이다.

특히 주문 요청의 결과가 불확실할 때 같은 주문을 무조건 다시 보내지 않도록 할 계획이다. 증권사의 주문·체결 내역과 대조한 뒤 다음 행동을 결정해야 중복 주문을 피할 수 있다. 시장 데이터가 끊기거나 계좌 상태가 맞지 않을 때는 새 주문을 멈추는 기준도 필요하다.

## 이제 무엇부터 만들까

첫 구현은 시세를 받고 1분 봉과 판단 기록을 남기는 것부터 시작한다. 그다음 뉴스·공시와 AI 분석을 연결하고, 가격 모델과 매매 판단을 단순한 기준선과 비교한다. 주문은 모의투자에서 충분히 시험한 뒤 연결한다.

지금 그린 구조가 정답인지는 아직 모른다. 앞으로 각 단계에서 **판단에 필요한 데이터가 제때 왔는지, 결과를 다시 재현할 수 있는지, 비용과 장애를 감당할 수 있는지** 확인하며 설계를 고쳐갈 예정이다. 다음 글에서는 세 입력 중 첫 번째인 실시간 시세 수집부터 자세히 다뤄보려 한다.
